Amazon Flat File Repair FLOW

把一次 Amazon flat file 上传失败拆成四个可复用阶段：Find 找证据、Leverage 利用已有信号、Optimize 只做安全文件修复、Win 用下一次 Processing Report 验证结果并整理人工分诊材料。

Find → Leverage → Optimize → Win

用一个闭环管理上传失败

1

Find

先收集 Processing Report、原始 flat file、模板版本、feed id、错误码、字段名、行号和 SKU family。不要一开始就改模板。

  • 把 8541、99010、90244 等错误码分组。
  • 标记缺少字段、枚举值错误和 catalog conflict。
  • 确认 parent、child、variation_theme 是否在同一 family 内一致。
2

Leverage

利用已有证据判断哪些问题能靠文件修，哪些必须人工确认。把 Seller Central 页面提示、Processing Report、flat file header 和此前上传结果放在同一个决策表里。

  • 优先用 report row 和 SKU 锁定责任字段。
  • 把 locked attribute、brand ownership、ASIN mismatch 单独列出。
  • 保留可复制给 Seller Support 的证据。
3

Optimize

只做低风险文件修复：补必填字段、统一 variation_theme、修正枚举值、修复父子体关系。不要把不确定的 catalog ownership 问题伪装成文件修复。

  • 先生成 manual review CSV。
  • 只导出通过安全复核的 repaired draft。
  • 重新上传前保留原始文件副本。
4

Win

用下一次 Processing Report 验证，而不是靠页面提示判断。减少的错误码进入 resolved list；仍然出现的错误进入人工分诊或 Seller Support brief。

  • 对比 before / after report。
  • 记录哪些 SKU family 已恢复 variation。
  • 把无法文件修复的问题转成脱敏 brief。

Decision Table

下一步应该做什么？

只有 Processing Report先上传报告，按错误码、SKU、行号和字段生成修复清单。 有 flat file 和 variation 问题补充 flat file，分辨文件可修、需要人工判断和 catalog conflict。 出现 ASIN / catalog conflict先读 8541、8036、90244 指南，再决定是否开 case。 需要人工复核提交脱敏 brief，附错误码、字段、行号、SKU family 和已尝试动作。

Cadence

一次修复循环的交付物

  1. Evidence packetProcessing Report、原始 flat file、模板版本和错误码分组。
  2. Repair candidate list按字段和 SKU family 标出可以直接修的内容。
  3. Manual review list把需要品牌权限、locked attribute、ASIN ownership 或 Seller Support 的事项单独输出。
  4. After-upload validation用下一份 Processing Report 验证错误是否减少，保留 before / after 对照。

Boundary

这个 FLOW 页面不做什么

它不是 Amazon 官方文档，也不是 Seller Support 替代品；它只把现有工具和内容页组织成一个可执行的修复闭环。真实 catalog ownership、品牌权限、locked attributes 和历史 ASIN 数据冲突，仍需要通过 Amazon 后台或支持渠道处理。
